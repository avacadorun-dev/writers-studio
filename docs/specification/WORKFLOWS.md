# «Студия автора»: функциональные workflow

> Версия: 0.8  
> Статус: dictation baseline и нормативный Assistant baseline; WF-37 реализован и локально проверен  
> Дата: 4 августа 2026  
> Цель: однозначное описание поведения для Product Design, Engineering и QA
> Реализация и доказательства: [TRACEABILITY.md](../implementation/TRACEABILITY.md)

Спецификация режима «Ассистент», MCP-каталог и provider contract:
[ASSISTANT_MODE.md](./ASSISTANT_MODE.md).

## 1. Правила чтения документа

- `WF-*` — пользовательский workflow.
- `S-*` — экран или крупное состояние интерфейса.
- `R-*` — обязательное продуктовое правило.
- `AC-*` — проверяемый acceptance criterion.
- Формулировка «система сохраняет» означает durable local или server condition, явно названный в шаге.
- Live partial, source transcript и manuscript — разные слои и не взаимозаменяются.

## 2. Сквозные правила

### R-01. Оригинал не перезаписывается

Записанное аудио и source transcript конкретного STT-запуска immutable. Исправления создают transcript draft или document revision.

### R-02. Partial не является документом

Нестабильная строка live-STT отображается, но не попадает в undo history, versions, search и export.

### R-03. Ручная правка имеет приоритет

Поздний batch-результат не изменяет документ, который пользователь уже редактировал. Он появляется как предложение сравнить.

### R-04. Запись и распознавание независимы

Если live-STT недоступен, запись продолжается локально. Пользователь видит деградацию, а не ложный stop.

### R-05. Успех обозначается только после сохранения

Нельзя показывать «Сохранено», если данные находятся только в оперативной памяти или неподтверждённой очереди.

### R-06. Редактор полноценный

После диктовки пользователь работает в Tiptap/ProseMirror editor, а не в `textarea` или read-only transcript.

### R-07. Опасные операции обратимы

Restore создаёт новую revision; удаление сначала помещает объект в корзину/grace period; конфликт сохраняет оба варианта.

### R-08. Голосовая команда явная

Команда требует префикса, визуального подтверждения и Undo. Настройка команд может быть отключена.

### R-09. Диктовка и ассистент — разные режимы

Диктовка создаёт transcript. Ассистент интерпретирует поручение через LLM и tools.
Фраза не меняет режим неявно и не переносится между ними автоматически.

### R-10. MCP не обходит доменную модель

Ассистент читает и изменяет проект только через versioned MCP tools, которые
вызывают те же application services и ownership checks, что обычный UI.

### R-11. Изменения ассистента сначала staged

Mutation tools формируют `AssistantChangeSet`. Canonical tree, document, dictionary
или version не меняются до явного применения пользователем.

### R-12. Риск определяет подтверждение

Чтение в выбранном scope выполняется автоматически. Создание и изменение входят в
общий preview. Чувствительные действия открывают native flow. Необратимые действия
недоступны модели.

### R-13. Контекст минимален

Выбор `Весь проект` означает право искать и читать нужное, а не отправку всей
рукописи одним prompt. Credentials, raw storage URLs и чужие данные не попадают в
model context.

### R-14. Provider capability проверяется

OpenAI-compatible label недостаточен. Для режима «Ассистент» подключение должно
пройти server-side probe text generation и последовательного tool/function calling.
Provider и model фиксируются на весь run.

### R-15. Руководство ассистента явно и версионируемо

Проект может иметь один root artifact `ASSISTANT.md`. Его active revision
автоматически входит в каждый confirmed assistant turn, но не может изменить
ownership, scope, tool policy или approval rules. Обычная заметка с инструкциями
не подменяет guide.

### R-16. Память проекта принадлежит проекту, а не модели

Словарь хранит написания, Project Memory — факты и решения, `ASSISTANT.md` —
правила письма. Все три слоя видимы, версионируемы и доступны через typed
application services/MCP; provider-side memory не является источником истины.

### R-17. Voice и Chat продолжают один Assistant run

`Голосом` и `Чат` меняют только input mode. Target, project context, guide,
provider/model, Activity и change sets общие. Переключение никогда не отправляет
незавершённый draft автоматически.

### R-18. Assistant не скрывает рукопись

На desktop Assistant является docked-состоянием Studio. Открытие Voice, Chat,
working или review не демонтирует manuscript editor, не теряет selection/cursor и
не превращает рукопись в отдельный route. Встроенный assistant preview никогда не
считается canonical text до Apply.

### R-19. Вторичный экран имеет явный путь назад

Settings и другие вторичные экраны не полагаются только на browser history.
Видимая кнопка `Назад` возвращает в ближайший рабочий контекст: из project/node
settings — в тот же Studio node, из project settings — в проект, без project
context — в список проектов.

### R-20. Чаты ассистента независимы, рукопись общая

Один проект может иметь несколько Assistant chats/runs. Переключение видимого
чата не останавливает работающий run, не объединяет его черновик или историю с
другим чатом и не меняет canonical manuscript. Любое предложение по-прежнему
привязано к base revision и становится stale при несовместимой параллельной правке.

## 3. Роли

### Автор

Единственная активная роль MVP. Может управлять только своими проектами.

### Система

В workflow под «системой» понимаются client, backend и background jobs как единое поведение. Техническое распределение описано в arc42.

## 5. Глобальная оболочка Studio

Desktop layout:

```text
┌────────────────────────────────────────────────────────────────────┐
│ Project name | Save status | Search | Dictate | Export | Profile  │
├──────────────────┬─────────────────────────────┬───────────────────┤
│ Project tree     │ Editor / Review workspace   │ Context panel     │
│ Parts            │                             │ Outline / source  │
│ Chapters         │                             │ stats / versions  │
│ Scenes           │                             │                   │
│ Drafts           │                             │                   │
├──────────────────┴─────────────────────────────┴───────────────────┤
│ Optional recording dock / audio player                            │
└────────────────────────────────────────────────────────────────────┘
```

Обязательные свойства:

- левая панель сворачивается;
- правая панель контекстная и не обязательна для основного ввода;
- manuscript остаётся главным визуальным объектом;
- recorder dock не перекрывает текущую строку;
- save status имеет состояния `Сохранение…`, `Сохранено`, `На этом устройстве`, `Нужна синхронизация`, `Конфликт`;
- в focus mode остаются текст, минимальный save status и выход из режима.

## 6. Общие состояния загрузки и пустоты

| Контекст | Loading | Empty | Error |
|---|---|---|---|
| Проекты | skeleton карточек | «Создайте первое произведение» | Retry без потери фильтра |
| Дерево | skeleton строк | initial chapter уже создана | «Не удалось загрузить структуру» |
| Документ | skeleton страницы | placeholder «Начните писать или надиктуйте» | локальная копия, retry |
| История | skeleton списка | «Именованных версий пока нет» | retry |
| Поиск | progress в поле | до запроса — подсказка; после — «Ничего не найдено» | retry |
| Экспорт | progress job | не применимо | повторить из того же snapshot |

Skeleton никогда не имитирует recorder: состояние микрофона должно быть буквальным и доступным.

## 7. WF-01 — первый вход

### Цель

Попасть в список проектов и понять основное обещание продукта.

### Основной поток

1. Пользователь открывает S-01.
2. Вводит email и проходит выбранный способ входа.
3. При первом входе видит короткий onboarding из двух тезисов:
   - «Надиктовывайте текст и сразу продолжайте редактировать».
   - «Запись сохраняется отдельно от рукописи».
4. Нажимает «Создать первый проект».
5. Открывается S-03.

### Альтернативы

- Возвратный пользователь попадает на S-02.
- Если есть recovery item, над списком проектов показывается banner «Найдена незавершённая запись» с действием «Восстановить».
- Marketing carousel и обязательная настройка всех preferences в MVP отсутствуют.

### Acceptance criteria

- AC-01. После первого входа можно начать создание проекта не более чем за одно основное действие.
- AC-02. Recovery banner нельзя скрыть навсегда, пока unsynced data не обработаны.

## 8. WF-02 — создание проекта

### Предусловие

Пользователь авторизован.

### Основной поток

1. На S-02 пользователь нажимает «Новый проект».
2. S-03 показывает:
   - рабочее название — обязательное;
   - тип: роман, рассказ, сценарий, нон-фикшн, свободный;
   - язык диктовки: русский / английский;
   - необязательная цель по словам.
3. Пользователь нажимает «Создать проект».
4. Система одной транзакцией создаёт Project и первую главу.
5. Открывается S-04 с пустой первой главой.
6. Фокус находится в названии главы или в первом абзаце — согласно последнему шагу onboarding.

### Валидация

- Название после trim: 1–120 символов.
- Дубликаты названий разрешены.
- Цель: целое число 1–10 000 000.
- Ошибка сервера не очищает форму.

### Acceptance criteria

- AC-03. Успешно созданный проект сразу доступен после refresh.
- AC-04. Частично созданного проекта без initial node не бывает.

## 9. WF-03 — управление структурой

### Основные действия

- создать часть, главу, сцену, черновик или заметку;
- переименовать;
- изменить статус: идея, черновик, редактура, готово;
- перетащить в допустимое место;
- дублировать;
- архивировать/переместить в корзину.

### Правила

- Перетаскивание имеет keyboard alternative «Переместить…».
- При перемещении изменяется дерево, а не document revisions.
- Глава может содержать сцены.
- Глава без сцен может содержать собственный текст.
- Если в главе уже есть собственный текст, добавление первой сцены не перемещает его автоматически; UI предлагает создать сцену из текста.
- Удаление непустого узла показывает количество вложенных элементов и помещает дерево в корзину.

### Acceptance criteria

- AC-05. После reorder активный документ и cursor не теряются.
- AC-06. Undo структуры доступен сразу после move/delete через toast.

## 10. WF-04 — ручная работа в редакторе

### Предусловие

Открыт content-bearing node на S-04.

### Основной поток

1. Пользователь ставит cursor и вводит текст.
2. Tiptap применяет локальную transaction.
3. Не позднее 1 секунды recovery snapshot/journal фиксируется в IndexedDB.
4. Header показывает «Сохранение…».
5. После 1,5 секунды idle либо 15 секунд непрерывной работы client отправляет revision.
6. После server acknowledgement header показывает «Сохранено».

### Доступные действия MVP

- undo/redo;
- paragraph;
- headings 1–3;
- italic, bold, underline, strike;
- blockquote;
- lists;
- link;
- scene break;
- find/replace;
- copy/paste;
- word count;
- focus mode;
- «Прослушать источник» для абзаца с provenance.

### Paste

1. Пользователь вставляет содержимое.
2. Система удаляет scripts, unsafe links, неизвестные styles/nodes.
3. Поддерживаемое семантическое форматирование сохраняется.
4. При значительной потере форматирования доступен toast «Форматирование было упрощено».

### Конфликт

1. Server отвечает, что base revision устарела.
2. Система сохраняет локальный вариант как отдельную конфликтующую копию.
3. Header показывает «Мы сохранили оба варианта».
4. Пользователь может открыть актуальный документ или свою копию.

### Acceptance criteria

- AC-07. Refresh после acknowledgement показывает тот же текст и форматирование.
- AC-08. Undo отменяет перенос transcript как одно действие.
- AC-09. Autosave не меняет cursor/selection и не прокручивает страницу.
- AC-10. Quality-pass STT не вызывает скрытую Tiptap transaction.

## 11. WF-05 — подготовка диктовки

### Триггеры

- глобальная кнопка «Диктовать»;
- кнопка микрофона в пустом документе;
- shortcut;
- mobile quick record.

### Основной поток

1. Открывается S-05.
2. Destination предзаполнен текущим документом. Пользователь может выбрать:
   - текущая сцена/глава;
   - новый черновик;
   - новая сцена;
   - голосовая заметка.
3. Язык предзаполнен настройкой проекта.
4. Голосовые команды можно включить или отключить; показывается текущий префикс.
5. Показывается выбранный микрофон и level meter.
6. При первом использовании browser запрашивает permission.
7. Выполняются preflight:
   - browser origin безопасен для microphone API (`HTTPS` или loopback
     `localhost`/`127.0.0.1`);
   - microphone track active;
   - доступно достаточно local storage;
   - поддерживается recorder format;
   - network status известен.
8. Пользователь нажимает «Начать запись».
9. UI немедленно переходит в локальное recording state.
10. Параллельно создаётся server session и live stream.

### Важное правило

Нажатие «Начать запись» не ждёт подключения STT, если локальный recorder готов. Если server session не создана, UI сообщает, что запись хранится на устройстве, и продолжает попытки.

### Ошибки

| Ошибка | Поведение |
|---|---|
| Permission denied | Инструкция для браузера, «Проверить снова», текстовый ввод остаётся доступен |
| Небезопасный LAN HTTP | Не запрашивать permission; объяснить требование HTTPS/localhost, показать переход на localhost, заблокировать Start |
| Нет микрофона | Выбор устройства или отмена |
| Storage критически мал | Старт блокируется с понятным объяснением |
| Offline до старта | Разрешить локальную запись с явной пометкой |
| Unsupported browser | Предложить поддерживаемый браузер / загрузить готовый файл |

### Acceptance criteria

- AC-11. При сохранённом permission начало локальной записи подтверждается ≤ 300 мс.
- AC-12. Destination и язык видны до начала.
- AC-13. Ошибка STT, permission denial, отсутствие устройства и блокировка
  небезопасного HTTP являются разными состояниями; Start доступен только на
  secure origin.

## 12. WF-06 — live-диктовка

### S-06: информационная иерархия

1. Явный индикатор «Запись идёт».
2. Duration.
3. Pause и Finish.
4. Live transcript.
5. Состояние соединения/сохранения.
6. Вторично: marker, словарь, команды.

### Основной поток

1. Автор говорит.
2. Текущий partial отображается облегчённым стилем и label «распознаётся».
3. При обновлении partial заменяется только текущий нестабильный диапазон.
4. `segment_final` становится обычным текстом live-черновика.
5. Новый partial начинается после stable content.
6. Аудиочанки сохраняются локально и загружаются независимо.
7. Status line показывает одно из:
   - «Запись и текст сохраняются»;
   - «Запись сохранена на устройстве, синхронизация…»;
   - «Запись продолжается, живой текст недоступен».

### Поведение live-текста

- Cursor пользователя не прыгает вслед за partial, если он просматривает предыдущий текст.
- Auto-scroll работает, только если пользователь находится у нижней границы.
- Stable text не должен визуально «мигать» при новом partial.
- Stable text во время active recording доступен для чтения и selection, но не редактируется; для исправления пользователь ставит запись на паузу.
- Если provider меняет finalized segment, изменение оформляется отдельным correction event; в MVP предпочтительно не менять stable segment до batch review.
- Uncertain confidence можно показывать только для finalized words/segments, а не как россыпь предупреждений во время речи.

### Управление

- `Пауза` приостанавливает запись и live stream, но не завершает session.
- `Завершить` запускает WF-10.
- `Маркер` создаёт timestamped note «Вернуться сюда».
- В нижней панели записи по умолчанию раскрыт компактный блок `Команды`: он
  показывает активный prefix, примеры доступных голосовых фраз и кнопки частых
  команд `Новый абзац`, `Начать диалог`, `Разделитель сцены`, `Метка`,
  `Отменить команду`. Блок можно свернуть, не останавливая запись.
- Кнопка команды выполняет то же детерминированное command action и создаёт ту же
  source annotation, что распознанная голосовая фраза; она остаётся доступна, даже
  если распознавание голосовых команд отключено.
- Закрытие вкладки вызывает browser warning, если session active.
- Shortcut не срабатывает внутри системного permission dialog.

### Acceptance criteria

- AC-14. Partial визуально отличим от stable text не только цветом.
- AC-15. Пользователь может читать предыдущий текст без принудительного scroll.
- AC-16. Recorder status доступен screen reader.
- AC-17. Страница не даёт начать вторую session поверх активной.
- AC-17a. Список голосовых команд и кнопки частых команд видны во время записи без
  перехода в Settings; все кнопки подписаны и доступны с клавиатуры.

## 13. WF-07 — голосовые команды

### Настройка MVP

По умолчанию команды включены с префиксом «Команда».

### Грамматика

| Фраза | Действие |
|---|---|
| «Команда, новый абзац» | Завершить текущий абзац |
| «Команда, начало диалога» | Начать новую реплику с русского длинного тире |
| «Команда, разделитель сцены» | Вставить semantic scene break |
| «Команда, пометка» + текст | Создать timestamped note |
| «Команда, отменить команду» | Отменить последнее command action |
| «Команда, вернись к первому абзацу» | Поставить запись на паузу и открыть первый абзац для правки |
| «Команда, вернись к третьему предложению» | Поставить запись на паузу и выделить третье предложение |
| «Команда, вернись к предложению» + точные слова | Найти предложение по словам и выделить его |
| «Команда, вернись к словам» + точные слова | Найти и выделить названный фрагмент |
| «Команда, вернись в конец» | Вернуться к текущему месту расшифровки |

### Поток

1. Команда поступает как finalized segment Live-STT либо как нажатие подписанной
   кнопки в раскрытом блоке `Команды`.
2. Для речи deterministic parser проверяет нормализованный префикс и grammar;
   кнопка передаёт безопасный allowlisted `commandKind` без LLM-интерпретации.
3. При точном совпадении или разрешённом `commandKind` segment получает type
   `command` и сохраняет источник выполнения.
4. UI выполняет действие и показывает chip, например «Новый абзац · Отменить».
5. Командный segment не входит в transcript draft как prose.
6. Если пользователь нажимает «Отменить», действие отменяется, а голосовую фразу
   можно «Вернуть как текст».
7. Команда перехода назад автоматически ставит recorder на паузу, прокручивает к
   найденному абзацу и открывает его inline-редактор с нужной фразой или предложением
   в selection.
8. `К концу и продолжить` атомарно сохраняет исправленный абзац в live transcript,
   возвращает viewport вниз и возобновляет запись.
9. Если точная цель не найдена, запись не останавливается, а UI просит назвать номер
   абзаца или более точные слова.

### Ограничения

- Свободный LLM не интерпретирует команды в MVP.
- Фраза без точного префикса остаётся текстом.
- При низкой confidence команда не выполняется, а предлагается как action.
- В Settings можно отключить команды или изменить prefix.
- Навигация ищет только в stable live text; partial text не редактируется.

### Acceptance criteria

- AC-18. Каждая выполненная команда имеет видимое подтверждение и Undo.
- AC-19. Командный текст остаётся доступен в source transcript annotation.
- AC-20. Отключение команд делает все голосовые фразы обычным текстом.
- AC-20a. Отключение распознавания голосовых команд не скрывает кнопки команд и не
  меняет их server-side allowlist/Undo semantics.

## 14. WF-08 — pause/resume

### Pause

1. Пользователь нажимает «Пауза».
2. Recorder flush текущий audio chunk.
3. Live stream flush/commit текущий turn.
4. S-08 показывает:
   - «Запись на паузе»;
   - duration записанной речи;
   - `Продолжить`;
   - `Завершить`;
   - `Исправить текст`;
   - `Прослушать последние 10 секунд`.
5. Микрофон не считается активно записывающим.

`Исправить текст` открывает stable content как transcript draft внутри той же paused
session. Голосовая команда перехода открывает найденный абзац прямо на его месте.
Сохранённая правка заменяет соответствующие live-сегменты атомарно и входит в
финальный draft; оригинальное аудио остаётся неизменным. `Продолжить диктовку` и
`К концу и продолжить` остаются доступными.

### Resume

1. Пользователь нажимает «Продолжить».
2. Проверяется microphone track.
3. При необходимости открывается новый provider stream внутри той же dictation session.
4. Новый chunk получает следующий sequence.
5. UI возвращается на S-06.

### Acceptance criteria

- AC-21. Pause boundary не теряет последние слова.
- AC-22. Resume не создаёт отдельную пользовательскую сессию.
- AC-23. Duration отличает общую длительность session от записанного аудио.

## 15. WF-09 — деградация сети и recovery во время записи

### S-07

Основное сообщение:

> Запись продолжается на этом устройстве. Живой текст временно недоступен.

Действия:

- продолжить;
- поставить на паузу;
- завершить;
- открыть подробности синхронизации.

### Автоматическое поведение

1. Client продолжает создавать local chunks.
2. Upload queue делает retry с backoff.
3. Realtime connection пытается восстановиться.
4. После reconnection:
   - live stream продолжается с нового provider turn;
   - UI не обещает восстановить пропущенные partial;
   - banner сообщает «Соединение восстановлено».
5. Полный batch после stop расшифровывает gap.

### Если local storage близок к заполнению

- Warning 1: «Осталось примерно N минут записи».
- Critical: система предлагает завершить; если browser write уже не гарантирован, recording state меняется на error и сообщает точную границу последнего сохранённого chunk.

### Acceptance criteria

- AC-24. Потеря WebSocket не останавливает MediaRecorder.
- AC-25. Пользователь понимает разницу между сохранением записи и live-текстом.
- AC-26. После recovery отсутствующие chunk sequences дозагружаются.

## 16. WF-10 — завершение и финализация

### Основной поток

1. Пользователь нажимает «Завершить».
2. UI меняет кнопку на progress и предотвращает повторный recorder stop.
3. Recorder flush final chunk.
4. Client сверяет local manifest и uploaded acknowledgements.
5. Server получает idempotent stop command.
6. Открывается S-09:
   - запись завершена;
   - загрузка аудио;
   - сборка;
   - финальная расшифровка;
   - итог.
7. Пользователь может уйти со страницы; processing продолжается.
8. После успеха появляется notification и S-10.

### Состояния S-09

| State | Текст | Можно уйти? | Действие |
|---|---|---:|---|
| `uploading` | «Сохраняем запись…» | Да, если local recovery durable | Оставить в фоне |
| `assembling` | «Проверяем аудио…» | Да | — |
| `transcribing` | «Готовим точную расшифровку…» | Да | Открыть live-черновик |
| `review_ready` | «Расшифровка готова» | Да | Проверить |
| `failed_recoverable` | «Аудио сохранено. Расшифровку можно повторить» | Да | Повторить |
| `missing_chunks` | «Нужно досинхронизировать запись с этого устройства» | Ограниченно | Повторить загрузку |

### Acceptance criteria

- AC-27. Двойное нажатие Finish не создаёт две batch-задачи.
- AC-28. Уход со страницы не отменяет уже durable finalization.
- AC-29. Ошибка batch не скрывает доступ к аудио/live-тексту.

## 17. WF-11 — проверка расшифровки

### Layout S-10

- сверху: session title, date, duration, source status;
- центр: transcript draft;
- снизу или справа: waveform/player;
- отдельная навигация по uncertain segments и markers;
- primary action: «Перенести в рукопись» или «Готово», если destination уже manuscript;
- secondary: «Сравнить версии распознавания», «Повторить расшифровку».

### Основной поток

1. Пользователь открывает review.
2. Player и transcript используют общую временную шкалу.
3. Клик по абзацу запускает аудио с ближайшего `startMs`.
4. Во время playback активный абзац подсвечивается.
5. Пользователь исправляет transcript draft полноценными базовыми операциями редактора.
6. «Следующее сомнительное место» перемещает cursor и аудио.
7. Неизвестное имя можно добавить в dictionary.
8. Сохранение draft использует обычные revisions.

### Сравнение live и batch

- Batch source выбран по умолчанию как более стабильный, пока ручных правок нет.
- Если тексты отличаются, UI не показывает технический diff автоматически во время первого чтения.
- Действие «Сравнить» открывает S-11.
- Deleted/inserted текст доступен screen reader.

### Acceptance criteria

- AC-30. Клик по абзацу запускает соответствующий аудиодиапазон.
- AC-31. Ручная правка source transcript создаёт draft, source остаётся неизменным.
- AC-32. Добавленный термин доступен следующей dictation session.
- AC-33. Playback не блокирует редактирование.

## 18. WF-12 — поздний batch и сравнение

### Триггер

Пользователь начал редактировать live draft/manuscript до создания batch source.

### Поток

1. Batch завершается.
2. Появляется unobtrusive banner:

   > Доступна более точная расшифровка. Ваши правки сохранены.

3. Действия: `Сравнить` и `Не сейчас`.
4. S-11 показывает current text и batch source:
   - unchanged;
   - предложенная вставка;
   - предложенное удаление;
   - замена.
5. Пользователь принимает изменение, группу или всё.
6. Каждое принятие формирует editor transaction.
7. `Принять всё` требует preview summary, но не destructive modal.
8. Undo доступен после закрытия diff.

### Правила

- Batch source read-only.
- Current text — base для применения.
- Если current text изменился в другой вкладке после открытия diff, accept пересчитывается или блокируется с предложением обновить.
- «Отклонить всё» не удаляет source artifact, только закрывает suggestion.

### Acceptance criteria

- AC-34. До нажатия Accept current document byte-for-byte не меняется.
- AC-35. Принятые изменения видны в revision history как «Применена финальная расшифровка».
- AC-36. Пользователь может прослушать source range из diff.

## 19. WF-13 — перенос расшифровки в рукопись

### Предусловие

Есть transcript draft или source artifact и выбран destination.

### Основной поток

1. Пользователь нажимает «Перенести в рукопись».
2. Если destination пуст, показывается preview расположения.
3. Если destination содержит текст, предлагается:
   - вставить в cursor;
   - добавить в конец;
   - создать новую сцену;
   - заменить — только через отдельный destructive flow с preview.
4. Система преобразует transcript paragraphs в Tiptap nodes.
5. Каждому абзацу назначаются `blockId` и `sourceRefs`.
6. Одна Tiptap transaction вставляет весь выбранный фрагмент.
7. Открывается S-04, вставка выделена кратковременно.
8. Toast: «Текст добавлен · Отменить».

### Acceptance criteria

- AC-37. Source refs переживают save/load.
- AC-38. Undo удаляет только вставленный фрагмент.
- AC-39. Существующий текст не заменяется по умолчанию.

## 20. WF-14 — словарь проекта

### Entry points

- S-15 из project navigation;
- «Добавить в словарь» в review;
- исправление слова с предложением запомнить;
- настройка перед dictation.

### Term fields

- каноническое написание;
- варианты произношения/ошибочного написания — необязательно;
- тип: персонаж, место, термин, другое;
- язык;
- активен/неактивен.

### Правила

- Словарь влияет только на будущие STT-запуски и явный re-transcribe.
- Добавление термина не делает project-wide replace.
- Delete имеет undo.
- Provider payload ограничивается релевантными активными терминами и его лимитом.

### Acceptance criteria

- AC-40. Пользователь видит, что словарь не исправляет старый текст автоматически.
- AC-41. Re-transcribe с обновлённым словарём создаёт новый artifact.

## 21. WF-15 — версии

### Autosave history

История может группировать частые revisions по времени, но named snapshots всегда видимы.

### Создание именованной версии

1. Пользователь нажимает «Сохранить версию».
2. Вводит название; по умолчанию дата и время.
3. Можно добавить заметку.
4. Snapshot ссылается на current acknowledged revision.
5. Если есть unsaved local change, сначала выполняется save.

### Сравнение

1. В S-12 пользователь выбирает две versions/revisions.
2. Diff показывает текст и базовое форматирование.
3. Можно перейти к changed block в editor.
4. Source refs в diff представлены действием «Аудио», а не техническими IDs.

### Восстановление

1. Пользователь нажимает «Восстановить эту версию».
2. Preview сообщает, что текущий вариант останется в истории.
3. Система создаёт новую revision с контентом snapshot.
4. Toast предлагает отменить восстановление созданием ещё одной revision.

### Acceptance criteria

- AC-42. Restore не удаляет более новые revisions.
- AC-43. Именованная версия не исчезает при компактизации autosave.
- AC-44. Version compare не изменяет document.

## 22. WF-16 — поиск и замена

### Поиск

- текущий документ: мгновенный локальный;
- весь проект: серверный индекс;
- result содержит тип, breadcrumb, snippet и match count;
- поиск не индексирует live partial;
- source transcript можно включить отдельным filter.

### Replace

- текущий документ: обычный replace/replace all;
- проект: обязательный preview по документам;
- каждый изменённый документ получает отдельную revision и общий operation ID;
- undo project-wide replace доступен через history operation.

### Acceptance criteria

- AC-45. Результат открывает документ и выделяет match.
- AC-46. Project-wide replace не применяется без preview.

## 23. WF-17 — экспорт

### Основной поток

1. Пользователь открывает S-14.
2. Выбирает:
   - весь проект или выбранные части;
   - формат DOCX, Markdown или TXT;
   - включать title page;
   - включать chapter titles;
   - включать notes — по умолчанию нет.
3. UI показывает ordered outline будущего файла.
4. Пользователь нажимает «Создать файл».
5. Система фиксирует consistent snapshot всех документов.
6. Background job собирает файл.
7. Пользователь получает download action.

### Ошибка

- Retry использует тот же snapshot, если пользователь не выбирает «Собрать заново».
- Недоступная node schema останавливает export и указывает конкретный документ.
- Аудио не включается в manuscript export.
- Полный backup проекта — отдельное действие.

### Acceptance criteria

- AC-47. Содержание exported file соответствует preview outline.
- AC-48. Редактирование во время job не меняет готовящийся файл.
- AC-49. Markdown/TXT доступны без потери пользовательского доступа после отмены подписки.

## 24. WF-18 — незавершённая запись после сбоя

### Обнаружение

При старте PWA Local Recovery Store находит session без завершённого manifest.

### S-16

Для каждого item:

- проект/destination, если известны;
- дата;
- сохранённая duration;
- local/remote chunk count;
- действия `Восстановить`, `Прослушать`, `Скачать аудио`, `Удалить`.

### Восстановить

1. Client проверяет checksums.
2. Создаёт/возобновляет server session.
3. Загружает missing chunks.
4. Запускает finalization.
5. После `review_ready` удаляет local chunks только по retention policy или подтверждению.

### Удалить

Если remote copy не подтверждена, dialog явно говорит:

> Эта запись существует только на этом устройстве. После удаления восстановить её нельзя.

### Acceptance criteria

- AC-50. Recovery работает без исходной вкладки.
- AC-51. Пользователь может скачать локальное аудио до удаления.
- AC-52. Local chunks не очищаются сразу после одного неуспешного upload.

## 25. WF-19 — удаление проекта

### Поток

1. Пользователь выбирает «Переместить проект в корзину».
2. Dialog перечисляет проект и связанные данные.
3. Проект скрывается из основного списка и доступен в корзине в течение grace period.
4. В корзине доступны `Восстановить` и `Удалить окончательно`.
5. Окончательное удаление требует ввода названия проекта или эквивалентного сильного подтверждения.
6. Запускается purge метаданных, аудио, artifacts и exports.
7. Audit сохраняет факт удаления без содержимого.

### Acceptance criteria

- AC-53. Архивирование и корзина не смешиваются.
- AC-54. После restore дерево и versions доступны.
- AC-55. UI не обещает мгновенное физическое удаление, если backup retention ещё действует.

## 26. Responsive workflows

### Desktop ≥ 1024 px

- полный Studio layout;
- editor и review;
- tree + optional context panel;
- live recorder может быть отдельным focus workspace.

### Tablet 768–1023 px

- одна side panel открыта одновременно;
- editor полноценный;
- waveform переносится под текст.

### Mobile < 768 px

Приоритет:

- quick record;
- live text;
- pause/resume/finish;

- markers;
- выбор destination;

Не требуется в первом MVP:

- сложный version diff;
- project-wide replace;
- полный export configurator;
- одновременные tree/editor/context panels.

Mobile не должен показывать disabled desktop UI. Недоступное действие объясняется и доступно позже на desktop.

## 32. WF-21 — формулирование поручения

### S-19

Desktop сохраняет Studio shell и строится как единый рабочий экран:

1. project tree — 240–280 px слева;
2. полноценный manuscript editor — центральная dominant region;
3. docked assistant panel — 340–440 px справа;
4. внутри панели: target/context/guide/provider, ordered transcript, stable/partial
   и uncertain states, literal microphone/run status и state dock;
5. текущий selection в рукописи виден одновременно со стенограммой и может быть
   прикреплён к turn без копирования текста в отдельный экран.

Assistant panel collapsible/resizable, но editor остаётся mounted и сохраняет
cursor, selection, scroll position, formatting, undo/redo и autosave state.

### Голосовой поток

1. Пользователь запускает Assistant; microphone начинает listening явно, как в
   диктовке, после permission/preflight.
   На небезопасном HTTP voice control disabled с объяснением и переходом в Chat
   или на localhost; создание Chat turn не блокируется.
2. Существующий STT-контур локально начинает захват без ожидания LLM.
3. Live partial и stable transcript постоянно видны в assistant panel, а
   рукопись и текущий selection — рядом в центральной области.
4. Короткая пауза только стабилизирует partial.
5. После тишины длиной preference `3/5/8 секунд` интерфейс показывает checkpoint
   `Выполнить поручение?`; default — 5 секунд.
6. Checkpoint имеет `Продолжить говорить`, `Исправить текст`, `Выполнить`.
7. Обычная речь или `Команда, продолжить` закрывает checkpoint и продолжает тот же
   transcript turn.
8. Checkpoint не имеет auto-submit: без ответа состояние остаётся waiting.
9. `Выполнить` или точная команда `Команда, выполнить поручение` flush/stabilize
   transcript, ставит microphone capture на паузу и запускает LLM turn.
10. Uncertain words и target можно исправить до этого подтверждения.
11. Создаётся durable `AssistantRun` или следующий `AssistantTurn` существующего
    run с фиксированным provider/model capability snapshot.
12. Первый запуск фиксирует отдельный безопасный снимок writer preferences для MCP:
    язык, command/live/editor параметры и silence threshold; hardware identifiers,
    credentials, retention/privacy и account controls в него не входят.

По умолчанию аудио поручения удаляется после durable instruction transcript.
Отдельная настройка может сохранять его; это не `Голосовая сессия` рукописи.

### Текстовый поток

Текстовый ввод открывает S-28 и следует WF-29. Пользователь пишет message,
проверяет target/context и явно отправляет. Пустой message не отправляется; этот
turn остаётся частью того же run.

### Target и project context

`Target` отвечает на вопрос «куда писать»:

- current selection, если есть;
- current document — default запуска из главы/сцены;
- новый draft/note — явный вариант;
- `Определится из поручения` — default глобального запуска из проекта.

`Project context` отвечает на вопрос «что можно читать»:

- весь текущий проект через MCP по мере необходимости — default;
- текущий раздел или выбранные материалы — privacy restriction.

Оба значения всегда видны до подтверждения. Whole-project context не вставляет
весь проект в prompt, а глобальный target не разрешает скрытую запись во все файлы:
реальные targets перечисляются в change-set preview.

### Acceptance criteria

- AC-59. Stable и partial transcript различимы; голосовое поручение можно исправить
  до первого LLM request.
- AC-60. На экране раздельно видны project, target, project context и provider/model
  текущего run.
- AC-61. LLM получает текст поручения; audio input не является обязательной
  capability provider.
- AC-62. Silence checkpoint никогда не отправляет поручение автоматически; refresh
  восстанавливает transcript, target, context и статус run/turn.

## 33. WF-22 — чтение проекта и подготовка результата

### S-20

Показываются:

- открытая редактируемая рукопись с сохранёнными cursor/selection;
- исходное поручение в сохранённой live-стенограмме в assistant panel;
- текущий этап: `Читает материалы`, `Ищет`, `Готовит изменения`;
- human-readable activity items и streaming answer/proposal под поручением;
- встроенный live preview для текстовых changes текущего документа с постоянной
  пометкой `Предложение · не применено`;
- `Остановить`;
- свёрнутые technical details;
- найденные source links по мере готовности.

Mic status — `На паузе, пока ассистент работает`. Экран не превращается в
классический чат: события образуют хронологический session feed без bubble avatars.
Это правило относится к live surface S-20; S-28 использует привычную chat
композицию, но тот же ordered run и tool semantics.

Не показываются raw chain-of-thought, credentials, полный system prompt и
необработанные provider payloads.

### Поток

1. Изолированный model step обязан ровно один раз вызвать
   `assistant.begin_turn(mode, summary)` по смыслу желаемого результата.
2. Сервер не классифицирует поручение регулярными выражениями, словарями
   глаголов/синонимов/гипонимов или иным лексическим router.
3. После декларации Orchestrator выдаёт полный разрешённый policy каталог MCP;
   модель выбирает read tools по смыслу и доступным структурным данным.
4. Read tools выполняются автоматически в scope.
5. Каждое tool event проверяет owner/project/run execution context.
6. Ответ без изменений может завершиться как `completed_no_changes`.
7. Mutation tools допустимы только после `mode=change` и пишут только в
   `AssistantChangeSet`.
8. Ответ без изменений завершает turn и показывает `Продолжить голосом` /
   `Продолжить в чате`.
9. Change set появляется в потоке. Пользователь может применить весь безопасный
   набор сразу либо открыть S-21 как modal поверх текущего Studio; route, editor и
   run при этом не меняются.
10. Inline preview не изменяет canonical revision/autosave/undo history. Если
    пользователь вручную изменил пересекающийся range, preview становится stale и
    Apply блокируется до пересчёта; ручная правка не отменяется.
11. `Продолжить голосом` создаёт следующий turn с теми же target/context, если
   пользователь их не изменил.
12. Run сохраняет guards duration, provider timeout и repeated failures. Число
    tool calls/provider cycles по умолчанию не ограничено; в настройках проекта
    автор может задать положительный лимит tool calls на одно поручение. Несколько
    буквальных целей одной revision читаются
    через `document.find_exact_batch`, а не серией одиночных вызовов. Две и более
    новые записи словаря или Project Memory стейджатся через соответствующий batch
    tool (до 100 items), а не расходуют один вызов на каждую запись. Один или
    несколько новых content-bearing узлов создаются сразу с начальным содержимым
    через `tree.create_nodes_batch` (до 50 siblings в порядке массива). Создать
    пустой staged-узел и обратиться к нему через `document.append` до Apply нельзя.
    Новое содержимое существующего документа объёмом более ~1 500 слов пишется
    серией `document.append_chunk`: до 9 000 символов / 1 500 слов за вызов,
    последовательные номера, одна приблизительная `targetWords` и одна итоговая
    staged document operation. Полный предыдущий чанк в provider replay не
    повторяется; передаются счётчики и короткий хвост для связности.
13. Один provider request ожидается до 10 минут. Chat Completions выполняется как
    SSE stream: host потребляет keepalive comments, последовательно собирает text,
    opaque reasoning и фрагменты tool arguments, но вызывает tool только после
    terminal event и проверки полного JSON. Timeout не повторяет дорогой запрос
    автоматически. Если mutation ещё не было, turn завершается как
    `provider_timeout`; если operations уже staged, они сохраняются как явно
    частичный change set для review.

### Stop

1. Пользователь нажимает `Остановить`.
2. Server-side execution context run помечается stopped; при вынесенном MCP его
   короткоживущий capability token отзывается.
3. Run и его текущий `working` turn атомарно получают `cancelled`; orphaned
   индикатор `working` после Stop недопустим.
4. Новые tool calls отклоняются.
5. Текущий provider request отменяется best effort.
6. Уже собранный ответ/change-set draft остаётся в S-22.

### Acceptance criteria

- AC-63. Read tool не может изменить canonical state.
- AC-64. Каждый tool повторно проверяет ownership и project scope.
- AC-65. Transcript, activity и streaming result остаются видимы в одном session
  feed; activity показывает действие и объект, но не раскрывает secrets/raw JSON.
- AC-66. После Stop новый tool call этого run не выполняется.
- AC-67. Ошибка provider/tool сохраняет instruction и уже подготовленный draft;
  завершённый turn предлагает продолжить голосом или в чате в том же run.
- AC-67b. Двухминутный idle cutoff не обрывает длинную Chat Completions генерацию:
  provider transport использует SSE keepalive, единый server-side
  `LLM_REQUEST_TIMEOUT=10m` применяется к системному и всем пользовательским
  провайдерам без connection-specific override, автоматического retry с повторной
  стоимостью нет.
- AC-67c. Provider timeout после staged mutation создаёт partial review, а timeout
  до mutation не создаёт пустой change set; в обоих случаях canonical state не
  меняется.
- AC-67d. Stop не оставляет `working` turn внутри terminal/cancelled run.
- AC-67e. Поручение на большой текст не требует одного provider response: 1–16
  чанков объединяются в один preview и одну revision после Apply; сбой сохраняет
  уже полученные чанки как partial, а незавершённая серия не маркируется готовой.
- AC-67f. Replay следующего long-form шага не содержит полный текст предыдущих
  чанков; continuity обеспечивают accumulated word count и bounded tail.
- AC-67g. Chat Completions отправляется с `stream=true`; OpenRouter SSE comments не
  интерпретируются как JSON, fragmented tool arguments собираются по call index, а
  незавершённый stream не приводит к выполнению частичного tool call.
- AC-67h. Mid-stream error остаётся recoverable и сохраняет только безопасные
  provider diagnostics; HTTP/edge 408, 504 и 524 классифицируются как timeout.
- AC-67a. Содержательное создание 1–50 sibling-узлов укладывается в один tool
  call, остаётся раздельно reviewable/applyable/undoable и не обращается к
  несуществующим до Apply node IDs.

## 34. WF-23 — review и применение change set

### S-21 layout

S-21 — крупный modal поверх текущего Studio, а не отдельный полноэкранный route.
Под modal остаются смонтированы manuscript, project tree и Assistant panel.

- основная область: manuscript diff или structural preview выбранного объекта;
- compact aside: change groups, исходное поручение, resolved target и sources;
- summary: количество документов, вставок, замен, перемещений и новых объектов;
- source links;
- primary `Применить изменения`;
- secondary `Попросить исправить`, `Отклонить`;
- сообщение `Ничего не изменится до применения`.

После открытия `Попросить исправить` обычный набор действий review полностью
скрывается. В форме одновременно доступны только `Отмена` и `Отправить`:
`Применить изменения` и `Отклонить` не могут находиться на экране рядом с
`Отправить`, потому что относятся к разным решениям пользователя.

### Поток

1. Пользователь просматривает change groups.
2. Может включить/исключить независимую group, если dependencies позволяют.
3. `Попросить исправить` создаёт следующий turn того же run и новый change-set
   version; предыдущий preview остаётся в Activity.
4. Перед Apply сервер повторно проверяет base project/tree/revisions.
5. Если base актуален, все operations применяются одной transaction.
6. Каждый document получает новую revision с `source=assistant`.
7. Все изменения получают общий operation ID.
8. Открывается S-22/applied state и toast `Изменения применены · Отменить`.

### Stale

Если хотя бы один base изменился:

> Проект изменился после подготовки. Обновите предложение.

Apply блокируется. Пользователь может пересчитать change set или открыть
актуальный документ; тихого rebase нет.

### Acceptance criteria

- AC-68. До Apply canonical project byte-for-byte не меняется.
- AC-69. Multi-document preview перечисляет каждый затронутый объект и тип действия.
- AC-70. Частичная server failure не оставляет часть change set применённой.
- AC-71. Stale base блокирует Apply.
- AC-72. Applied revisions содержат run ID, operation ID и assistant provenance.
- AC-73. Group Undo восстанавливает все затронутые объекты компенсирующими revisions.
- AC-74. Source transcript и original audio не изменяются assistant change set.
- AC-74a. Пока открыта форма исправления предложения, Apply/Reject отсутствуют;
  Cancel возвращает обычные review actions, Send создаёт следующий turn.

## 35. WF-24 — чувствительные и необратимые действия

### A3

Для export, archive/trash, restore и retranscribe Assistant:

1. объясняет подготовленное действие;
2. вызывает только `prepare_*` tool;
3. открывает существующий native flow с заполненными параметрами;
4. пользователь подтверждает в обычном UI;
5. native workflow сохраняет свои preview/confirmation/idempotency правила.

`prepare_*` возвращает типизированный server-authored destination, а не URL от
модели. Параметры native flow переносятся без потерь; IDs повторно проверяются на
owner/project membership. Restore несёт expected current revision и блокируется,
если документ изменился после подготовки. Provider, credentials, privacy и writer
settings изменяются только пользователем в native UI и не имеют mutation tool.

### A4

Purge project/account, local-only recovery delete, credentials/privacy/retention
changes не имеют model tools. Ассистент может только объяснить, где найти действие.

### Acceptance criteria

- AC-75. Model tool registry не содержит commit, purge или credential-read tools.
- AC-76. A3 не выполняется без native confirmation.
- AC-77. Prompt или project content не может расширить allowed tools/scope.

## 37. WF-26 — системный и пользовательский LLM provider

### S-23

Показывает:

- read-only `Системный` provider из env, если configured;
- пользовательские connections;
- status/capabilities/last check;
- выбранный default для Assistant;
- `Добавить провайдер`.

Системный key никогда не показывается и не копируется в user connection.

### S-24 fields

- display name;
- base URL;
- dialect: Auto / Responses / Chat Completions;
- API key;
- model ID;
- advanced secret headers;
- context limit при необходимости.

Timeout не редактируется в S-24: единый server-side `LLM_REQUEST_TIMEOUT`
(baseline `10m`) действует для системного и всех пользовательских подключений.
Сохранённое подключение не может вернуть прежний скрытый лимит `120000 ms`.

Primary action: `Проверить подключение`. Save доступен после явного результата
проверки. Status `Ограничен` можно выбрать для Assistant, только если пройдены
обязательные text + strict/sequential tool-result capabilities; UI явно показывает
необязательные ограничения вроде отсутствия streaming. Результат без обязательных
capabilities имеет status `Несовместим` и для Assistant недоступен.

### Server-side probe

1. TLS/SSRF/redirect policy.
2. Auth.
3. Text generation.
4. Function/tool call со strict arguments.
5. Tool result в следующем turn.
6. Два последовательных calls.
7. Optional streaming/parallel/structured outputs/remote MCP/usage.

Транзиентный сбой одной попытки не должен навсегда кэшировать ложный
`Несовместим`: server повторяет полный probe один раз. Если повтор проходит,
connection получает status `Ограничен` и явную пометку о нестабильности; отменённый
request не повторяется.

### S-25

Показывает capability summary понятным языком:

- `Подходит для ассистента`;
- `Текст работает, инструменты недоступны`;
- `Не удалось подключиться`;
- конкретный исправимый класс ошибки.

### Acceptance criteria

- AC-81. API key после submit не возвращается клиенту и виден только masked.
- AC-82. System env credential нельзя прочитать или изменить через UI/MCP.
- AC-83. Connection без последовательного tool calling нельзя выбрать для Assistant.
- AC-84. Probe не сохраняет invalid credential как активное подключение.
- AC-85. Provider/model не переключается посередине run.
- AC-86. Удаление connection запрещает новые runs, но не ломает history.

## 38. WF-27 — руководство ассистента проекта

### S-26

В корне каждого проекта может быть один специальный artifact `ASSISTANT.md`.
Пользовательское название — `Руководство ассистента`.

Точки входа:

- Project tree → `Проектные файлы`;
- Assistant session header → badge `Руководство активно`;
- empty state, если guide отсутствует;
- command palette.

### Создание

1. Пользователь выбирает:
   - пустой файл;
   - структурированный шаблон;
   - `Предложить по рукописи`.
2. Первые два варианта открывают native editor.
3. Третий запускает read-only анализ выбранных глав и создаёт staged guide draft.
4. Пользователь просматривает preview и применяет его как первую revision.
5. Никакие стилистические правила не генерируются и не активируются молча.

### Редактирование

Native editor предлагает необязательные секции:

- голос и тон;
- лицо, время и фокализация;
- ритм, длина фраз и диалоги;
- канон и приоритет источников;
- словарь и обязательные написания;
- нежелательные слова, клише и приёмы;
- положительные/отрицательные примеры.

Guide имеет save status, autosave recovery, versions и restore-as-new-revision.
Ссылки на dictionary/note/document выбираются через picker и сохраняют stable IDs.
Baseline limit — 24 000 символов.

### Использование

1. При подтверждении каждого `AssistantTurn` backend загружает active guide строго
   по project artifact ID.
2. Run/turn сохраняет guide artifact ID и revision ID.
3. Session header показывает active/missing и позволяет открыть guide.
4. Изменение guide во время working turn не меняет уже собранный prompt; новая
   revision применяется со следующего confirmed turn.
5. Явное поручение turn может переопределить stylistic default.
6. Guide не меняет ownership, project context, allowed tools, A0–A4 или Apply.
7. Файл не входит в manuscript/export по умолчанию.

### Acceptance criteria

- AC-87. Проект без `ASSISTANT.md` полностью работоспособен и не получает скрытых
  сгенерированных stylistic rules.
- AC-88. В проекте не может быть двух active assistant guides.
- AC-89. Каждый confirmed turn фиксирует exact guide revision или явное `none`.
- AC-90. Targeted и global Assistant используют один и тот же active project guide.
- AC-91. Текст из обычной заметки не может подменить guide или расширить policy.
- AC-92. Assistant-generated create/update guide всегда проходит change-set preview.
- AC-93. Restore guide создаёт новую revision; активный working turn не меняется.
- AC-94. Guide отсутствует в manuscript/export по умолчанию и не возвращается в
  search results читательского текста.

## 39. WF-28 — словарь и память из live-поручения

### Голосовой сценарий

1. В S-19 автор говорит: `Запомни, Элина не умеет плавать. А имя Элина добавь в
   словарь; Эля — вариант`.
2. После silence checkpoint автор подтверждает turn.
3. LLM семантически объявляет `mode=change`, читает словарь/память и предлагает
   два typed результата без server-side keyword matcher:
   - dictionary record типа `character`;
   - project-memory record типа `character`.
4. При неоднозначности `словарь / память / руководство` Assistant задаёт
   уточнение в том же live feed и предлагает `Продолжить голосом`.
5. MCP read tools проверяют дубликаты и конфликты.
6. Mutation tools создают две staged operations.
7. В session feed появляется компактное summary; S-21 показывает оба объекта.
8. После Apply records получают revisions и общий operation ID.
9. Следующие turns находят факт через `project_memory.search` и имя через словарь.

### S-27

Project Memory показывает:

- statement;
- kind;
- active/inactive/always-relevant status;
- scope;
- tags;
- source references;
- created/updated source: user/assistant;
- revision/history.

Есть search, filters, `Добавить факт`, `Изменить`, `Деактивировать`, `История`.
Удаление по умолчанию заменяется deactivation; restore создаёт новую revision.

### API/MCP invariants

- MCP и обычный UI/API используют один application service;
- staging дедуплицируется по provider tool-call ID; update mutation требует
  optimistic base revision, а Apply — единый operation ID;
- duplicate candidate не создаётся молча — показывается merge/update choice;
- для 2–100 новых записей одного типа обязательны `dictionary.add_batch` или
  `project_memory.add_batch`; сервер разворачивает items в независимые reviewable
  operations и возвращает индекс каждого typed conflict;
- batch не меняет canonical state, partial Apply и grouped Undo: он только не даёт
  большому цельному поручению упереться в защитный лимит tool calls;
- exact dictionary spelling доступно STT и Assistant после committed revision;
- memory retrieval возвращает source/revision и не притворяется certainty модели;
- `alwaysRelevant` меняется только явно и является A2.

### Acceptance criteria

- AC-95. Явное voice-поручение может подготовить dictionary и memory records в
  одном change set.
- AC-96. До Apply словарь и память byte-for-byte не меняются.
- AC-97. Dictionary record хранит canonical spelling, variants и type; pronunciation
  optional.
- AC-98. Memory record хранит kind, statement, scope, sources, tags и revision.
- AC-99. Дубликат/конфликт предлагает merge/update и не создаётся молча.
- AC-100. Следующий turn может получить committed record через typed read/search
  tool с project ownership check.
- AC-101. Provider-side memory не используется как project source of truth.
- AC-102. Group Undo компенсирует dictionary и memory revisions одной operation.

## 40. WF-29 — переключение Voice / Chat

### Точки входа

- segmented switch `Голосом / Чат` в S-19/S-20/S-28;
- fallback CTA при denied/unavailable microphone;
- keyboard shortcut из Assistant workspace;
- mobile switch над session feed.

### Voice → Chat

1. Если voice turn не начат, S-28 открывается сразу в том же run.
2. Если listening active, microphone ставится на паузу и partial flush выполняется
   best effort.
3. Unconfirmed transcript остаётся видимым.
4. UI предлагает:
   - `Перенести в чат`;
   - `Вернуться к голосу`;
   - `Удалить черновик`.
5. `Перенести в чат` копирует transcript в composer без provider request.
6. `Вернуться к голосу` продолжает тот же durable draft; `Удалить` требует
   намеренного нажатия и удаляет только unconfirmed draft.
7. Только `Отправить`/`Ctrl/Cmd+Enter` создаёт
   `AssistantTurn(inputMode=text)`.

### S-28

Показывает:

- ту же открытую рукопись и project tree, что S-19/S-20;
- docked chat panel справа, а не отдельную full-screen chat page;
- общий chronological run history;
- сообщения автора и ответы Assistant;
- human-readable tool activity/sources/change-set cards;
- persistent target, project context, guide revision и provider/model;
- sticky multi-line composer;
- project-object/selection attachments;
- `Остановить` во время tool loop;
- `Проверить изменения` для ready change set.

Chat mode не запускает STT, не создаёт audio и не использует silence checkpoint.
Это привычный chat UI, но project mutations сохраняют те же preview/Apply/Undo.
Переход Voice ↔ Chat не remount-ит editor и сохраняет selection, cursor, scroll,
manual undo history и неприменённый assistant preview.

### Chat → Voice

1. После terminal/recoverable turn пользователь выбирает `Голосом`.
2. Создаётся следующий voice draft в том же run.
3. При необходимости выполняется microphone preflight.
4. История S-28 остаётся доступна; S-19 показывает тот же ordered session feed.

Во время provider/tool work switch доступен для просмотра, но composer/recorder
не принимает новый turn; queueing нескольких поручений не входит в baseline.

### Acceptance criteria

- AC-103. Voice и Chat используют один run ID и общий ordered history.
- AC-104. Переключение сохраняет target/context/guide/provider/change set.
- AC-105. Active listening ставится на паузу; transcript не теряется и не
  отправляется автоматически.
- AC-106. Chat message отправляется только явным Send/keyboard submit.
- AC-107. Chat turn не создаёт STT/audio artifacts.
- AC-108. Text и voice turns различимы в Activity, но не разделены на разные
  conversation histories.
- AC-109. Tool work использует одинаковые MCP/policy/preview/Undo semantics
  независимо от input mode.
- AC-110. При недоступном microphone Chat остаётся полностью работоспособным.

## 43. WF-30 — центральный сценарий адресной голосовой редактуры

### Сценарий

1. Автор заканчивает диктовать сцену и открывает Assistant в том же проекте.
2. Stable scene revision и source transcript остаются доступными; новый Assistant
   turn не создаёт dictation session.
3. Автор говорит: `Сделай диалог менее прямолинейным, но не меняй последнюю реплику`.
4. Live transcript показывает uncertain имя. Автор исправляет его до `Выполнить`;
   только исправленная confirmed instruction становится immutable turn input.
5. LLM читает ProjectStructure, текущую scene revision и dialogue blocks через
   MCP, затем определяет все целевые реплики и последнюю protected реплику. UI
   показывает target chips и chip `Защищено: последняя реплика`.
6. Если «диалог» или персонаж разрешаются неоднозначно, Assistant задаёт вопрос
   в том же feed; mutation tools до ответа не вызываются.
7. Read tools получают exact base revision. Для одного буквального фрагмента
   модель вызывает `document.find_exact`, для нескольких — один
   `document.find_exact_batch`; возвращённые block-local Unicode anchors и
   `expectedText` копируются в одну mutation с edits и protected ranges.
8. Сервер проверяет, что proposal не меняет protected range и не выходит за
   resolved scope.
9. S-21 показывает trace `поручение → найденные фрагменты → diff`, а последняя
   реплика отображается как неизменяемый context.
10. Независимые document/dictionary/memory groups имеют checkbox. Зависимая group
    автоматически включает prerequisite или объясняет, почему её нельзя выбрать.
11. Apply фиксирует только выбранные groups одной transaction и общим operation
    ID. `Отменить` создаёт компенсирующие revisions для всей applied selection.
12. Следующим turn автор говорит: `Обнови карточку Марины по этой сцене`.
13. Assistant читает уже применённую revision и предлагает отдельную
    Project Memory/character-card group с source reference на сцену.
14. Канон не меняется до второго явного Apply.

### Производительность и длинные sessions

- stable transcript появляется с той же задержкой, что live STT диктовки;
- checkpoint UI не ждёт LLM;
- после подтверждения `RUN_STARTED`/working state durable до сетевого запроса;
- первый activity item должен появиться не позже первого завершённого read/tool
  шага; UI не показывает фальшивый progress;
- event stream возобновляется с последнего sequence после reload/reconnect;
- run не пересылает всю рукопись: используются manifest, search/range tools и
  bounded outputs;
- многофрагментная правка не расходует один provider cycle на каждый абзац:
  `document.find_exact_batch` индексирует до 50 буквальных целей одной revision;
- повторная доставка provider/tool event дедуплицируется по call/idempotency key;
- длинный run может compaction-ить provider context, но durable feed, pinned guide
  revision, targets, applied operations и source links не теряются.

### Acceptance criteria

- AC-111. Assistant правит ранее надиктованный stable fragment без создания новой
  dictation session и без изменения source transcript/audio.
- AC-112. Позиционная, scope- и entity-ссылка разрешается в stable node/block/range
  IDs и exact base revision.
- AC-113. Неоднозначная ссылка блокирует mutation и требует уточнения.
- AC-114. Исправление transcript до Execute попадает в confirmed instruction без
  лишнего provider request.
- AC-115. Protected range проверяется сервером и остаётся byte-for-byte /
  subtree-equivalent неизменным.
- AC-116. Review показывает связь instruction, resolved targets, tool activity и
  каждой diff group.
- AC-117. Независимые groups можно исключить; зависимости валидируются до Apply.
- AC-118. Выбранные groups применяются атомарно и отменяются единым grouped Undo.
- AC-119. Обновление канона/карточки по сцене является отдельным связанным change
  set с source reference и отдельным Apply.
- AC-120. Reload/reconnect длинной session продолжает ordered event stream без
  дублирования applied operations.

## 44. WF-31 — Assistant в проектах с динамической структурой

1. При создании проект получает versioned structure template. Роман использует
   manuscript, сценарий — screenplay, GDD — game-design, свободный проект —
   минимальный folder/document template.
2. UI строит tree, create menu, breadcrumbs и labels из `ProjectStructure`, а не
   из глобального enum.
3. Каждый Assistant run читает `project.get_structure`; tool definitions не
   перечисляют фиксированные литературные node kinds.
4. `tree.create_node`, `tree.create_nodes_batch` и `tree.move_node` принимают
   stable type key и проверяют `canBeRoot/allowedChildren` в application service.
   Для content-bearing node batch-вариант сразу принимает начальное содержимое и
   не требует обращения к staged node до Apply.
5. Change set фиксирует structure revision. Изменение schema после preview делает
   структурные operations stale.
6. Custom type с `contentBearing=true` получает обычный editor/revisions/search;
   structural type без content не создаёт пустую manuscript revision.
7. Неизвестная модели label не препятствует работе: tool result содержит key,
   label, capabilities и breadcrumb.

### Acceptance criteria

- AC-121. Assistant/MCP не содержит allowlist `part/chapter/scene` как источник
  истины; допустимые kinds берутся из project schema.
- AC-122. Невалидное вложение отклоняется сервером и не попадает в canonical tree.
- AC-123. Screenplay, GDD и free/custom templates создают разные начальные node
  types и labels, оставаясь совместимыми с теми же tools.
- AC-124. Structure revision участвует в stale-check структурного change set.
- AC-125. UI имеет fallback для нового type key и не теряет доступ к его content,
  revisions или Assistant actions.

## 45. WF-32 — семантический turn protocol без лексического router

### Контракт

1. Первый provider request содержит только текущее подтверждённое поручение,
   наличие/отсутствие target и единственный tool `assistant.begin_turn`.
2. Model обязана вызвать его ровно один раз с `mode=answer|change|clarify` и
   непустым `summary`.
3. `change` выбирается по требуемому изменению состояния проекта, даже если автор
   просит только подготовить diff и пока не применять его.
4. `clarify` выбирается только когда недостающее нельзя получить чтением проекта.
   Его `summary` является прямым вопросом пользователю; второй provider request с
   устаревшей history не выполняется.
5. После `change` основной tool loop получает текущее поручение как единственный
   авторитетный user input. Предыдущий proposal читается только через
   `assistant.get_recent_change_set`, включая rejected/applied state.
6. После декларации доступен полный каталог проекта в рамках policy. Host не
   выбирает tools по словам поручения.
7. `document.find_exact` и `document.find_exact_batch` выполняют только буквальную
   индексацию известных строк. Они не интерпретируют `второй абзац`, `эта сцена`,
   имя персонажа или намерение.
8. UI показывает Markdown-ответ и human-readable activity; `<think>/<analysis>`,
   raw JSON, tool names и UUID не являются основным пользовательским контентом.

### Acceptance criteria

- AC-126. Каждый turn имеет ровно одну валидную semantic declaration до project
  tool calls; отсутствие/дубликат/невалидный mode завершает turn контролируемой
  ошибкой.
- AC-127. В intent routing отсутствуют regex, verb/synonym/hyponym lists и
  instruction-to-tool keyword allowlist.
- AC-128. После declaration модель получает полный policy-разрешённый MCP catalog;
  mutation tool отклоняется сервером для `answer/clarify`.
- AC-129. Запрос `исправь предложение` читает последний native change set и не
  может принять prose старого assistant message за состояние проекта.
- AC-130. Exact replacement использует anchors из `document.find_exact` или
  `document.find_exact_batch`, `expectedText`, base revision и server-validated
  protected ranges; ручной неверный offset не меняет canonical документ.
- AC-131. Thinking скрыт, Markdown семантически отрендерен, а primary activity и
  review используют понятные действия/объекты вместо raw tool names и UUID.

## 46. WF-33 — единый Assistant workspace с live manuscript preview

### Desktop contract

1. Запуск Assistant из Studio оставляет открытый `nodeId` на экране и открывает

2. До открытия panel manuscript использует обычное floating-представление Studio.

## 47. WF-34 — ссылки словаря и заметки на полях рукописи

1. Автор выделяет непустой фрагмент внутри одного верхнеуровневого блока
   рукописи. Выделение не создаёт постоянную панель над текстом: правая кнопка
   мыши открывает рядом с указателем компактное меню `Связать со словарём` /
   `Добавить заметку` / `Прикрепить к ассистенту`. Клавиатурный эквивалент —
   `Shift+F10` или клавиша контекстного меню, touch-эквивалент — долгое нажатие.
   Выделение через границу блоков не создаёт неоднозначный якорь и получает
   понятное объяснение.
2. Действие `Связать со словарём` из контекстного меню открывает поиск по реальным терминам текущего
   проекта. После выбора термин отображается transient inline-decoration и по
   клику открывается в панели полей.
3. Действие `Добавить заметку` создаёт заметку к той же точной цитате. Текст
   заметки можно изменить, пометить исправленным, вернуть в работу либо удалить
   без изменения рукописи.
4. Якорь хранит `blockId`, Unicode code-point offsets, `exactText`, контекст и
   base revision отдельно от Tiptap JSON. Создание и перепривязка проверяются
   сервером против указанной revision.
5. При ручной правке редактор отображает anchors через ProseMirror mapping и
   передаёт их вместе с autosave. Revision и новые позиции фиксируются одной
   транзакцией.
6. Если диапазон удалён, изменён вне редактора или больше не может быть доказан,
   пометка сохраняет цитату и получает независимый `anchor_status=detached`;
   её жизненный статус `open/resolved` не подменяется, а похожий текст не
   выбирается эвристически.
7. Старый клиент без `annotationAnchors` не удаляет пометки. Conflict copy и
   Duplicate копируют их; удаление словарного термина сохраняет snapshot ссылки.
8. На desktop выбранная пометка открывается в панели полей, на mobile — в нижнем
   sheet. Оба представления дают одинаковые действия и не меняют editor Undo.

### Acceptance criteria

- AC-143. Правый клик, `Shift+F10`/клавиша меню и долгое нажатие открывают
  контекстные действия только для непустого выделения; постоянной панели над
  рукописью нет. Выделение внутри одного блока создаёт серверно проверенный
  Unicode-safe exact anchor, межблочное отклоняется с понятным сообщением.
- AC-144. Реальный термин словаря отображается inline, открывает актуальную цель и
  сохраняет читаемый snapshot после удаления цели.
- AC-145. Заметка отображается inline, редактируется, решается, возвращается и
  удаляется из панели полей.
- AC-146. Decorations не входят в canonical document JSON и editor Undo/Redo.
- AC-147. Ручная правка переносит доказуемые anchors в той же SQL-транзакции, что
  и новая document revision.
- AC-148. Удалённый или недоказуемый диапазон не привязывается к похожему тексту:
  исходная цитата сохраняется с `anchor_status=detached`, независимо от
  жизненного статуса `open/resolved`.
- AC-149. Save старого клиента без anchor field не удаляет пометки и не смещает
  их наугад.
- AC-150. Revision conflict и Duplicate не теряют пометки; ownership и входные
  anchors проверяются сервером.
- AC-151. Desktop-панель и mobile-sheet дают функционально одинаковый доступ к
  словарной ссылке, тексту заметки и её статусу.

## 48. WF-35 — все правки проекта и переносимый формат

1. Пункт `Правки в тексте` открывает единый список заметок и словарных ссылок во
   всех неудалённых документах проекта.
2. Список поддерживает поиск по заметке, цитате, термину и документу, а также
   фильтры по типу, статусу и документу. Решённые пометки остаются доступны.
3. `Перейти` открывает Studio нужного node с `annotationId`, раскрывает панель,
   ставит exact selection и прокручивает цитату в видимую область.
4. Additive migration не меняет старые revisions и Tiptap schema. Экспорт v2
   переносит пометки отдельно; импорт принимает v1 без пометок и v2 с полной
   проверкой ссылок и атомарным ID remap.
5. Future format, повреждённый anchor или ссылка отклоняются до commit. Старый
   importer также отклоняет v2 до создания частичного проекта.

## 49. WF-36 — Assistant исправляет заметки проекта одним проходом

1. Assistant получает проектный список заметок через read-only MCP и может
   отфильтровать его по документу, типу, жизненному статусу и состоянию якоря.
2. Для исправления Assistant передаёт только stable annotation ID, собственную
   revision заметки, ожидаемую цитату, замену и предложение `resolve`. Block ID и
   offsets вычисляет и проверяет сервер по текущему exact anchor.
3. До Apply система группирует исправления по документам и показывает в review
   текст заметки, прежнюю цитату, точную замену и отдельный переключатель
   `После применения отметить исправленной` для каждой заметки.
4. Apply одной SQL-транзакцией создаёт document revision, детерминированно
   переносит все anchors документа, применяет выбранные lifecycle-переходы и
   пишет immutable before/after history. Заметки не удаляются.
5. Exact replacement всего отмеченного диапазона заменяет anchor exact text и
   context; правка до диапазона сдвигает offsets; partial overlap, удаление или
   недоказуемое изменение оставляют цитату и переводят anchor в `detached` без
   семантического угадывания.
6. Изменившиеся после staging annotation revision, expected text или document
   revision делают change set stale до начала commit. Undo создаёт
   компенсирующую document revision и восстанавливает прежние anchor/lifecycle
   snapshots; audit history переживает удаление Assistant run.

### Acceptance criteria

- AC-161. `annotation.list` и `annotation.get` читают только пометки текущего
  owner/project и не раскрывают provider прямого доступа к БД.
- AC-162. `annotation.propose_fixes` принимает не более 50 versioned исправлений,
  не принимает model-supplied offsets и не меняет canonical state до Apply.
- AC-163. Review показывает note, exact before/after и независимо управляемый
  будущий `resolved/open` статус каждой выбранной заметки.
- AC-164. Apply атомарно меняет документ, anchors, lifecycle и immutable history;
  заметка после исправления остаётся доступной.
- AC-165. Anchor mapping детерминирован; partial overlap и deletion не используют
  fuzzy/semantic reattachment и сохраняют исходную цитату как `detached`.
- AC-166. Stale annotation/document revision или expected-text mismatch не
  оставляют частично применённых документов, anchors либо lifecycle changes.
- AC-167. Grouped Undo восстанавливает текст и before-snapshots пометок, а audit
  before/after сохраняется после удаления Assistant run history.

## 50. WF-37 — несколько чатов ассистента в одном проекте

> Статус: реализовано и локально проверено 4 августа 2026; S-38–S-41 и Mobile
> P-11 являются текущим product baseline.

1. В заголовке assistant panel пользователь видит название текущего чата,
   activity status, `Новый чат` и `Скрыть панель` как разные действия.
2. Открытие selector показывает S-38 с приоритетными секциями `Нужно внимание`,
   `В работе` и `Недавние`. Это переключатель поручений, а не общий event log.
3. `Новый чат` открывает S-39. Проект, текущий документ, provider/model и active
   guide наследуются явно и видимы до отправки; пользователь может изменить scope.
4. Durable `AssistantRun` создаётся только после явной отправки первого turn.
   Закрытие пустого compose не оставляет чат в истории.
5. После отправки пользователь может вернуться к рукописи, открыть другой чат или
   создать следующий. Невидимые working runs продолжают работу в пределах
   серверной concurrency policy; переключение не является Stop/Cancel.
6. Draft, target, activity, input mode и review state принадлежат конкретному run.
   Один chat может ждать review, пока другой работает или принимает новый turn.
7. Готовность, ошибка и необходимость review создают status/unread marker и
   поднимают чат в `Нужно внимание`; просмотр terminal result снимает unread, но
   не удаляет durable activity.
8. Каждый change set хранит base revision. Если другой чат или ручная правка уже
   изменили тот же документ, S-40 блокирует Apply, показывает base/current revision
   и предлагает пересчитать предложение на текущей основе.
9. На tablet список открывается оверлеем над Studio; на mobile — отдельным
   полноэкранным состоянием. В обоих случаях manuscript editor остаётся mounted и
   восстанавливает cursor, selection и scroll.

- AC-170. Переключение или скрытие панели не отменяет provider/tool work и не
